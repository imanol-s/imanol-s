# Errors and assertions

**Assertions for internal contracts; error handling for external input.** Validate data from files, users, networks, and other systems at the boundary with real error handling. Inside the boundary, assert preconditions and invariants that only internal callers can violate, and do not re-validate in every helper. When adding a new input path, route it through the existing validation boundary. Assertions may be stripped in production, so never guard external input with one. Convert a "this should never happen" comment into a raise or assert at the point the assumption is made.

**Match the system's error stance.** Decide whether a system halts on bad state (correctness) or continues degraded (robustness) by reading how existing code behaves, then match it in the routine you add. Crash early on an impossible internal state rather than substituting a silent default. Do not crash at a boundary with untrusted input, in a long-running batch where partial progress would be lost, or where resources need cleanup.

**Define errors out of existence before handling them.** When callers repeatedly wrap a call to ignore "not found", "already exists", or "empty", change the contract (idempotent delete, clamp, return empty) and remove the caller handling. When the error cannot be defined away, handle it once: low in the stack where recovery is possible, or in one handler around a group of sibling calls. Do not mask by retrying a non-idempotent operation, and do not define away a failure the caller must know about (data loss, failed write to an external system, security check). Exceptions vs values follows the language: exceptions where that is the idiom (Java, C#, Python, Ruby); result or error values where that is the idiom (Go, Rust, C, functional code). Use values for expected frequent outcomes (not found, validation failure) even in exception languages.

**The default branch of a closed set raises.** When a switch or if-chain covers an enum or status set, make the else or default branch raise or log an explicit unexpected-value error rather than fall through to a default behavior.

## The problem

Making the same SAP change across many records means repeating a sequence of clicks, field edits, and saves. Interrupted batches introduce another problem: knowing what completed before deciding where to continue.

I built Automaton to automate those workflows while keeping their progress and outcomes visible.

## My contribution

As the solo developer, I designed and implemented the project end to end: browser automation, reusable infrastructure, workflow adapters, the desktop interface, run journals, and tests.

As a computer science graduate, I approached Automaton as a software engineering problem. The challenge was to coordinate browser state and workflow-specific behavior while keeping a durable record of execution.

## Removing an unnecessary wait

One field-read condition treated a valid blank value as though the field had not finished loading. That triggered repeated browser checks before accepting the value already returned.

I refined the condition to distinguish a resolved blank from an unresolved field. The recorded duration for that check changed from **8.0 seconds to approximately 0.1 seconds**, while unresolved fields retained their readiness checks. Browser probes for that check changed from **approximately 80 to 1**.

## Architecture around what varies

Python and Selenium drive an existing, signed-in Chrome session. A PySide6 desktop interface and command-line tools use the same underlying workflows.

I separated workflow orchestration from browser adapters and shared infrastructure. Common services handle page readiness, record processing, and recovery. Each adapter retains the rules for identifying records, editing fields, and confirming its workflow's result.

This boundary makes reuse practical: a new workflow can share infrastructure while keeping its own behavior explicit.

## Recording execution

Run journals capture outcomes and provide checkpoints for supported resume paths. They help distinguish completed work from skipped, failed, or interrupted steps.

I kept workflow-specific journal semantics alongside shared persistence mechanisms. Different workflows can preserve the evidence they need without forcing every operation into the same recovery model.

Supported recovery paths can discard a stranded draft or restore a session. Some failures require operator review before continuing.

## Correctness and verification

Offline tests exercise input handling, workflow logic, journals, and interface behavior without a live SAP connection. Separate live checks establish whether SAP displayed the expected screen and persisted a change.

Keeping these checks distinct makes the evidence easier to interpret.

## The result and takeaway

Automaton combines batch execution, an operator interface, and resumable run records in one tool for SAP data maintenance.

The engineering takeaway is to share stable behavior and preserve meaningful differences. Explicit workflow boundaries, execution records, and verification steps make the automation easier to extend and inspect.
